# gglearn — Training Academy

A training academy for our brands. Learners pick a track (subject, product, service, tool, technology or process),
set a goal, and climb 20 levels from **Novice to Titan**. Built from the TrialTest / SkillsTest exam platforms,
rebuilt as a learning product with onboarding, offboarding and a question bank that improves from real results.

## Run it

```bash
npm install
cp .env.example .env.local        # set SESSION_SECRET (openssl rand -hex 32); ANTHROPIC_API_KEY optional
npm run db:push                   # create tables in data/gglearn.db
npm run seed                      # admin user (password printed once), sample brand, TrialTest import
npm run dev
```

## The maps (`lib/lifecycle/`)
`/map` is a transit map of how something is run, from first idea to closing it. A map is a definition (`MapDef`: lanes, phases, stops, handoff gates, areas, company stages, optional sizes) that `engine.ts` turns into a layout and routes. Three are listed in `maps.ts`: **Any business** (the default, `/map`), **Public sector** (`/map/public`, a UK public service or programme) and **Software** (`/map/software`). Add one by writing a definition and listing it.
- **Stages** pick the stops that matter for where a company or service is. **Sizes** (Startup, Small, Medium, Large, Enterprise, on the business and public maps) dim the stops that can wait until an organisation is bigger, and change who usually owns a stop, how formal a handoff is and what usually goes wrong. A stop in no size list matters from the smallest size.
- Links carry the choice: `/map/public?stage=case&size=large`. `npm run check:maps` checks every definition: ids, gates, stages, sizes, and overlapping labels.
- **Entry by problem** (`lib/lifecycle/problems.ts`, `businessMore.ts`, `otherProblems.ts`): the box at the top of every map. Someone types what is wrong in their own words (or ticks several common situations, or types a stop's name) and the map lights only the stops that help, with one thing to do today, how they will know it worked, and where learning stops and a professional begins. A problem is `{ say, words, stops, first, done, pro? }`; matching is on words, weighted so rare words count more. A link carries it (`/map?problem=cash`, or `problem=cash+late` for several). The stage picker also has five quick questions for people who cannot say which stage they are in. **What people pick is counted, anonymously** (`lib/problemLog.ts`, table `problem_picks`, `/admin/problems` for the platform owner): per day, per map, how often each problem was picked, a stop was typed, or a search found nothing. No account, address or typed text is stored; ids are checked against the map and the call is limited per address. It needs `npm run db:push` once (until then logging does nothing and the page says so). `npm run check:problemlog` tests it.
- **Stop text** (`businessText.ts`, `businessMore.ts`, `publicText.ts`, `softwareText.ts`): on every map every stop has its own "where it usually breaks" and "you will know it worked when" (a stop without its own would show the failure note of the next handoff gate, which is about the handoff). Some stops add "the handover that matters" (`handoffs`), "where learning stops" (`pros`) and a note that rules differ by country (`local`). `npm run check:maps` fails if a stop lacks its own words.
- **Kind of business** (`businessSectors.ts`): a third lens beside stage and size. Someone says what they run (food and hospitality, retail, trades, professional services, health and care, education, making, technology, charity) and every stop that the sector changes shows an extra note ("In Food & hospitality: ..."). The sector panel says who sets its rules, the rules to expect and the stops that matter most, and each sector is also a problem in the finder (so "I run a cafe" finds it). Links carry it (`?sector=food`). A sector is `{ label, watch, rules, key, notes, say, words, first, done }`; `npm run check:maps` checks its stops exist.
- **How well the question bank backs each stop** (`scripts/report-stop-coverage.ts`, `content/lifecycle/coverage-business.json`): many stops share one learning track, so a stop can sit on a track with thousands of questions and have almost none about its own subject. `npm run report:coverage` counts, per stop, the track questions whose topic or prompt mention the stop's own words (a keyword count, so indicative) and lists the thin ones; `-- --write` saves it, and each stop card then says "Thin match", "Partly covered" or "Well covered". Re-run it when the question bank changes a lot.
- The business and public-sector content is a draft for review by someone who works in that field. The public-sector map has its own learning tracks (brand `public-sector`, eight tracks `ps-*`, 128 questions in `content/public-sector/`); a reviewer can edit the JSON and re-run `npm run import:knowledge`.

## Starting points (`lib/credits.ts`)
A person's level in a track is the highest of three things, and the map shows which one it came from (a diamond marks a level that is not an exam pass):
- **Exams passed**: saved per person, remembered on every sign-in.
- **The placement check** (`lib/placement.ts`): a short assessment that finds where to start.
- **A starting level** (`level_credits`): given by a manager or admin with a reason, or confirmed from what the person's job role normally holds (`suggestedStarts`, which uses the ladder's first ask per track, capped at level 10). It can end on a date and be taken back; rows are never deleted.

Starting levels lift where someone starts and unlock what comes next (`levelsPassed`). They are not exam passes: certificates still need the exam, and required training and promotions (`levelsEarned`) ignore them unless an admin marks one **counts as complete**. Managers can give up to level 10 to people they run (never themselves); admins any level. Managers use **Starting points** in the admin (`/admin/starting-points`) or open a map as someone they run (`/map?as=ID`, or `/map/software?as=ID`). `npm run check:credits` tests the rules.

## Race to Titan (gamified layer)
- **Rival per subject**: `lib/rivals.ts` gives every track a stable named rival who earns XP every day (deterministic, so no jobs needed). Rival level = XP / 150. Your level = levels passed. The head-to-head is drawn on the track page and dashboard.
- **Visuals**: `components/` holds SVG avatars that evolve through 5 ranks (Initiate, Adept, Expert, Master, Titan), rank shields, race track, score rings and confetti. No image assets.
- **Weekly league** (`lib/league.ts`, `lib/leagueRules.ts`, `/league`): eight tiers, Bronze to Diamond. The first time in a week someone scores (or opens the page after playing before) they are placed in a cohort of up to 30 in their tier, arena and audience, and keep it all week. Points are the weekly season's (100 a level, 10 a practice day). When the week ends the top fifth of each cohort move up and the bottom fifth move down; cohorts under 5 are never relegated, nobody is promoted on zero points, and the last settled row says where someone plays next. The first time it ever runs it settles only the latest finished week and closes the earlier ones without moving anybody. People hidden from the boards are not in it. Settling runs from `progressionFor`, so it needs no extra job. `npm run check:league` tests it.
- **Sign in with an emailed link** (`lib/loginLink.ts`, `/signin`, `/signin/<token>`): passwordless sign-in for an existing account. Asking gives the same reply for any address and is limited per address (5 an hour) and per visitor (10 an hour); the token is random, stored only as a hash, works once, lasts 15 minutes, and a newer link cancels an older one. Opening the link does NOT sign anyone in (mail scanners open every link): it shows "Sign in as Ana?" and only the button signs in. It leaves the password and the person's other sessions alone, and honours `?next=` for paths inside the site only. Needs `RESEND_API_KEY`, `MAIL_FROM` and `SITE_URL`. Google and Microsoft sign-in are not built: they need client credentials from those companies. `npm run check:signinlink` tests it.
- **Forgot your password** (`lib/passwordReset.ts`, `/forgot`, `/reset/<token>`): by email, on top of the manager-set temporary password (which still works). Asking for a link gives the same answer whether or not the address has an account, the email is sent without waiting for it so the timing does not give it away, and every ask counts against a limit per address (3 an hour) and per visitor (10 an hour). The token is random, stored only as a hash, works once, lasts an hour, and asking again cancels the earlier link. Only active accounts can be reset. Using it sets the new password, ends every other session, emails a "your password was changed" notice, and signs the person in. Needs `RESEND_API_KEY`, `MAIL_FROM` and `SITE_URL`; without mail the page says so and points to a manager. `npm run check:reset` tests it.
- **Where you belong** (`lib/membership.ts`, `components/WhereYouBelong.tsx`): a person belongs to a company through a company scope, a brand of it or a project of it, and what that means is decided by how many companies it is: none or several put them in the open arena with gglearn's own look; exactly one puts them in that company's arena with its look. The profile explains it in plain words ("Where you belong"), the dashboard, league and seasons pages carry a one-line note for people in several companies, and when a manager changes someone's companies (`updateScopes`) the person gets a notification saying what changed and what it means for them (changes within the same company, such as a company scope becoming one of its brands, say nothing). A check confirms the words match the real arena and look logic. `npm run check:membership` tests it.
- **Contest moderation** (`lib/contestAdmin.ts`, `/admin/contests`): the organiser can always cancel their own contest. An admin can cancel a contest, or switch off its invite link, only when its organiser is someone they run (the same tenancy rule as people, topics and rewards): a company's admin moderates that company's people's contests; contests run by another company, by an individual with no company, or by the platform itself belong to the platform owner (an admin with no company scope). Managers and learners moderate only their own. `/admin/contests` lists exactly the contests an admin may moderate, with filters and paging; the platform owner can also show the public campaign rounds. The public campaigns are always owned by a platform owner, never by a company's admin (that would list them only inside that company), and `syncCampaigns` hands any round started by the wrong owner back. The setup notes on `/campaigns` are shown only to the platform owner. `npm run check:contestadmin` tests it.
- **Friends** (`lib/friends.ts`, `/friends`, `/f/<code>`): mutual and agreed, never a public follow. Two ways in: a personal friend link (the code is the same signed code as the referral link; whoever opens it and presses the button is a friend at once, both having consented) or a request by email that the other person accepts. Asking by email gives the same answer whether or not the address has an account; declining or removing tells nobody; at most 15 requests waiting and 200 friends. Friends see each other's first name and initial, this week's XP (quests and exams), the streak, and a feed of real things from the last 14 days: a level passed for the first time, a badge, a certificate. A topic is named only if the person looking could see it themselves, otherwise it says "a topic". A friend can cheer one event once (it must be in their own feed), and the person cheered is told. People who are not friends see none of it. `npm run check:friends` tests it.
- **Honest social proof** (`lib/proof.ts`): real numbers about what people are doing, shown only when they say something. A people-count appears only when at least 5 people are behind it (`MIN_SHOWN`), so a small number never looks sad and never points at an individual; below that nothing is shown, never a zero. The landing page can show people who practised this week, levels passed this week, certificates earned and people racing now (kept five minutes in memory); each topic page can show people learning it and people who passed a level in the last 30 days; a race with nobody in it says "Be the first to join" and its simulated rivals are labelled as such. Nothing is invented or rounded up. `npm run check:proof` tests it.
- **Personal Google and Microsoft sign-in** (`lib/social.ts`, `/auth/[provider]`, `components/SocialButtons.tsx`, Connected accounts on `/profile`): OpenID Connect like company SSO, for individuals. Nothing shows until the platform owner sets `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` and/or `MICROSOFT_CLIENT_ID` / `MICROSOFT_CLIENT_SECRET` in `.env.local` (redirect addresses to register: `<site>/auth/google/callback` and `<site>/auth/microsoft/callback`). A person is identified by the provider's own stable id, and an email is believed only when the provider vouches for it (Google `email_verified`; Microsoft: a personal account, or a work account whose domain Microsoft marks verified, `xms_edov`). A known identity signs in; an email on a domain a company has claimed for single sign-on is sent to that company's sign-in; an email that already has an account is never linked automatically (the owner signs in normally and connects the provider from their profile, so nobody can take over an account that was pre-registered with their address); otherwise a new account is made exactly as open sign-up makes one, carrying the referral and "tried it" topic. The last way in cannot be removed. Apple is not built (it needs a signed client secret and form-post). `npm run check:social` tests it.
- **Single sign-on** (`lib/sso.ts`, `lib/ssoAdmin.ts`, `/sso`, `/sso/go/[slug]`, `/sso/callback`, company section in `/admin/setup`): a company connects its OpenID Connect provider (Okta, Microsoft Entra ID, Google Workspace, Auth0, Keycloak...). Authorization-code flow with PKCE, state and nonce kept in a short-lived signed cookie; the ID token's signature (RS256 or ES256 only), issuer, audience, expiry and nonce are checked. Only an email on a domain the company claimed can come in (a domain belongs to one company; public webmail domains cannot be claimed), and only into an account that belongs to that company alone, so an account made by open sign-up with the same address, one in two companies, or the platform owner is never taken over. "Create accounts on first sign-in" is off by default. Requiring SSO (no password or emailed link for learners and managers; admins keep their password) can only be switched on after a first successful SSO sign-in has proved the setup works. The client secret is stored encrypted (AES-GCM, key from `SESSION_SECRET`: if that changes, enter the secret again), and the provider fetches are limited to public https addresses. `npm run check:sso` runs a mock provider and tests the flow and every way it can go wrong.
- **Directory sync** (`lib/scim.ts`, `lib/scimHttp.ts`, `/api/scim/v2/*`, company section in `/admin/setup`): SCIM 2.0 for Okta, Entra ID, Google Workspace and others. An admin makes a bearer token per company (shown once, only its hash kept, 3 live at most). The directory creates people as learners in that company (set up exactly like an invited joiner, with no password), updates names and emails, and switches people off or on; removing someone switches them off, signs them out everywhere and starts the offboarding checklist, never deleting. It can only see and change people it manages for that company: never an admin or manager, anyone in another company, or someone with no company; an existing learner of that company alone is adopted. Filters `userName eq` and `externalId eq`, paging, PATCH in both Okta and Entra styles. `npm run check:scim` tests it.
- **Cross-company league** (`lib/openLeague.ts`, `/league`, company branding form in `/admin/setup`): the weekly league normally keeps a company's people in that company's arena. Playing against other companies needs two yeses: an admin who runs the company switches it on (`companies.leagueOpen`, off by default) and the person chooses it (`users.openLeague`, off by default). Only people with both go into one shared arena (`x`); they are then not in their own company's league, and others see only first name, initial and points, never the company. Switching off, by either side, takes effect at once (the unsettled place this week is dropped and re-made in the right league), and a company switching it off also withdraws everyone's choice, so turning it on again never puts anyone back without a new yes. People with no single company are already in the open arena and have nothing to choose. `npm run check:openleague` tests it.
- **Classes** (`lib/classes.ts`, `/teams`, `/teams/[id]`, `/t/[token]`): a team started as a class has a teacher (the owner). The teacher sets assignments ("reach level N in this public topic within so many days") and sees, per student, whether each is done, late or open and when they last practised on those topics: nothing else (no other topics, XP, streak or email). Students are told exactly this on the join page before joining, see only their own assignments, and there is no board. Done is worked out from real exams. Joining a class puts a student on the assigned topics. `npm run check:classes` tests it.
- **Mentoring** (`lib/mentoring.ts`, `/mentoring`, `/m/[code]`): a mentee shares their signed mentor link; the mentor presses one button to agree, so both have said yes. The mentor sees the mentee's week, streak, certificates, goal and topics (a topic the mentor could not see themselves shows as "a topic"), never their email, and can send short notes (140 characters, 5 a day per pair). Either side can end it at any time without telling the other. Up to 3 mentors per mentee and 25 mentees per mentor. `npm run check:mentoring` tests it.
- **Parents** (`lib/mentoring.ts`, `/mentoring`, `/p/[code]`): the same two-sided consent as mentoring with `kind = parent`. The child shares their own parent link, the parent presses one button, and either side can stop at any time. A parent sees the same limited summary as a mentor (never an email) and can send a short kind note. Up to 4 parents per child and 10 children per parent, counted separately from mentors; nobody can be both for the same person. Covered by `npm run check:mentoring`.
- **Sponsors** (`lib/sponsors.ts`, `/sponsoring`, `/sp/[code]`): a learner picks a topic they can take and a level above where they are, and shares a signed link for that one goal. A sponsor presses a button to back it, and sees only the learner's first name, the goal, progress on it and, once reached, the verifiable certificate if there is one. Reaching the goal is recognised when the pass is awarded (`lib/rewards.ts`), so a pass held for an integrity review does not count until cleared; both sides are told once. Either side can end it silently. Up to 5 sponsors per goal, 5 open goals per learner and 25 goals per sponsor. No money moves. `npm run check:sponsors` tests it.
- **Search** (`lib/search.ts`, `lib/searchRules.ts`, `/api/search`, `/search`, `components/SearchPalette.tsx`): a header button and Ctrl/Cmd+K open a palette that searches pages, topics, races, and the asker's own teams and certificates. Who is asking decides what is found: topics are the ones they could pick (a stranger: only public ones, the landing page's rule); races are the ones listed to them, and a race's topic is searched and shown only if they can see that topic, so search cannot list a company's own topic names; teams and certificates are only theirs; pages depend on the kind of account; people are never searched. Words match in any order, accents and case ignored; better matches (exact, starts with, word starts with, contains) come first. At least two letters, 120 requests a minute per address. `/search` is the same with no JavaScript. `npm run check:search` tests it.
- **First win in about a minute**: a new sign-up (with no invite and no page to return to) lands on `/try?first=1`, picks one of a dozen topics and answers three questions. Done while signed in, it enrols them in the topic and counts as the day's quick drill (+30 XP, a streak started, the welcome streak freeze), but only when three different questions were really answered there (`completeTrial` in `lib/trial.ts`, once per topic per day). The level-check page now offers "Skip the check and start now" as a full button beside "Find my level first". The dashboard's next step then moves on to the study guide.
- **Try it before signing up** (`lib/trial.ts`, `/try`): a visitor with no account picks a public topic, answers three easy stored multiple-choice questions with instant feedback, sees a score, and is offered a free account that starts them on that topic (the sign-up form carries `try=<topic>`; the topic is enrolled only if a stranger may try it). Nothing about a guest is stored. Only public topics (the landing page's rule) and level 1-2 multiple-choice questions can be tried; the right answer is never sent with a question, only returned by the server after one is given, limited to 60 checks an hour per address. `npm run check:trial` tests it.
- **Celebration moments** (`lib/celebrate.ts`, `components/CelebrationToast.tsx`): the few events someone would want to show off (a badge, a player level-up, a league promotion, a top-three weekly or monthly finish) are real notifications the app already records. The newest unread one from the last three days is shown once as a toast with confetti and a one-tap share; sharing or dismissing marks it read so it never returns. The share card is rebuilt from real data when pressed (league promotions and duel wins have their own card kinds), so a toast can never share something that did not happen. `npm run check:celebrate` tests it.
- **Live duels** (`lib/duelRules.ts`, `lib/duel.ts`, `/d/<code>`): five multiple-choice questions, 15 seconds each, the same for two people at the same moment, or one person against a labelled simulated rival. Plain polling (about once a second), no websockets. Every moment comes from the server's clock and from when answers arrived; the schedule is never stored, it is worked out from the start time and the answers' own times, and a question closes early when both have answered. The state sent to a browser never holds the right answer to an open question or what the other player chose; both appear at the reveal. Questions are the topic's stored multiple-choice ones at levels each player has already passed (the drill rule, so a duel never shows an exam's questions). Right answers are worth 100 plus up to 50 for speed. Finishing with three or more answers counts as the day's quick drill (keeps a streak). A duel nobody joins is dropped after 15 minutes. `npm run check:duelrules` and `npm run check:duel` test it.
- **Streak freezes** (`lib/freezes.ts`): an instant reward that keeps a streak alive over a missed day. One welcome freeze on first activity, then one more for every 7 days in a row; hold at most 2. They are spent automatically the next time the person opens the app, only when they can cover every missed day of a streak of 2+ days (otherwise nothing is spent). A frozen day counts for the streak and its badges but is not practice: XP, quests and recaps ignore it. A small ledger (`streak_freezes`) remembers what was paid and spent; everything else is worked out from real activity. `npm run check:freezes` tests it.
- **Daily quests** (study guide +20, 5-question instant-feedback drill +30, finish an exam +40 XP) feed streaks and badges (`lib/stats.ts`).
- **Study guides** (`lessons` table) show the level syllabus plus flip cards from that level's questions.
- **Certificates** are issued on passing levels 5, 10, 15 and 20 and verifiable at `/cert/<code>`.
- **Import from the questions repo**: `npm run import:questions -- git-titan "Git: Novice to Titan" git "GIT & GITHUB"` (repo at `../questions`, override with `QUESTIONS_DIR`). It dedupes, maps numeric/text difficulty onto 20 levels, turns `topics.json` progressions into syllabi, and lists invalid JSON files it skipped. Re-running on a track that already has questions will add duplicates at shifted levels, so clear that track's questions first.

## How it works
- **Tracks and levels**: `lib/levels.ts` defines the 20 levels. Each attempt draws 10 fresh questions for the level,
  favouring ones the learner has not yet answered correctly. 80% passes and unlocks the next level.
- **Questions**: `mcq`, `open`, `scenario`. Open answers are graded by Claude against a reference answer and rubric
  (`lib/grading.ts`). Without `ANTHROPIC_API_KEY` a coarse keyword fallback is used.
- **Knowledge first**: authored questions link to a `knowledge_items` row, the single source of truth for a track.
- **Improvement loop**: `/admin` flags questions that are nearly always failed or never failed, for review or retirement.
- **People**: `/admin/people` onboards someone (checklist + auto-enrol by job role) and offboards them
  (access ends immediately, offboarding checklist and handover notes).
- **Company-scoped admin** (`lib/tenancy.ts`): a manager or admin with no scopes runs the whole academy (the platform owner, as before). One with scopes runs only those companies, brands and projects and what is beneath them: they see only people and tracks in that reach, can only add or move people within it, and cannot edit shared things (career ladders, the role-by-pillar matrix, the whole-academy question bank, shared academy tracks). The server actions enforce this, not just the pages. `npm run check:tenancy` tests it. Contest moderation is scoped too (see **Contest moderation** below).
- **Set up** (`/admin/setup`, `lib/setup.ts`): admins add companies (platform owner only), brands (to a company they run) and empty tracks (to a brand they run). Slugs come from the name and are made unique. A new track has no questions, so nobody is required to take it until questions are imported and approved. Tested by `npm run check:tenancy`.
- **Company branding** (`lib/brand.ts`, `/admin/setup`): a company can set an academy name, an accent colour, a logo (PNG, JPEG or WebP, 150 KB) and the issuer printed on certificates. A person who belongs to exactly one company (through a company, brand or project scope) sees that look in the header, footer, page title, buttons and headings; people in several companies, or none, and signed-out pages see the gglearn default. Certificates carry their holder's company look for whoever opens them. The colour must be dark enough for white button text. Not yet branded: the 20 level names, the sign-in page and the landing page. The schema gained four columns on `companies`, so run `npm run db:push` (the deploy script does).
- **Arenas** (`lib/arena.ts`): who competes with whom. A person who belongs to exactly one company is in that company's arena; everyone else (several companies, none, or the platform owner) shares the open arena. Season boards, team/company/role boards and the winners line only mix people from one arena, and each arena is ranked and settled on its own (seasons settled before this change keep their old global ranks). Public contests are listed and openly joinable only inside the organiser's arena, except contests run by the platform owner (the weekly and monthly campaigns), which are for everyone. An explicit invitation still works across arenas, and a public contest can still be watched by its link.
- **Company and brand profile → training** (`lib/profile.ts`, `lib/profilePublish.ts`, `/admin/profile`): a company or brand answers what a joiner needs to know, in sections that cover the whole organisation: identity, goals, people and structure, offer, customers, legal, finance, tools and access, ways of working, risk, plus who to contact for what, security, devices and AI use, joining and the first 90 days, pay and benefits, leaving and moving on (notice, handover, last day, winding down a project or brand), glossary, role guides, standards and change, engineering and operations, data and AI in use, sales and marketing, learning, and suppliers. Each section says when it is taught (`Section.by`: day 1, week 1, 30, 60 or 90 days; default 30). Publishing makes one track per phase that has answers: the original `profile-<scope>-<id>` track for the first 30 days (so earlier publishes stay put), plus `-d1`, `-w1`, `-d60` and `-d90` tracks. New tracks are required by default: of everyone (day 1 and week 1 pass level 3, due day 1 and day 7; later phases level 5, due day 30, 60 or 90) or, for sections only some families need, of those families (below). A policy an admin sets at `/admin/paths` is never overwritten by publishing again, and an existing track keeps the tier it already has. **Role-family tiering** (`lib/roleFamily.ts`, `Section.needs`): the careers roles are mapped onto the framework's seven families (ENG, PDS, DEL, OPS, COM, CORP, LEAD; a few roles are moved, such as delivery manager to DEL and security to OPS), and a section can be required of some families only (for example finance of CORP, DEL and LEAD; engineering and operations of ENG and OPS). Such sections go into their own track (`profile-<scope>-<id>-<phase>-<families>`), tier "role", with `roles` set to `family:eng` style tokens rather than a copied list of job roles, so a role added later is covered at once and `requirementsFor` (`lib/paths.ts`) matches a person through their family. Everyone else can still read the track; a role the academy cannot place in a family is held only to sections for everyone. If a section's audience or phase changes, publishing moves its text, history and reading records to the right track (questions written for the old track stay with it; use **Write questions** for the new one). The partly-specialist (S) and awareness (A) tiers of the framework are not enforced: awareness is just open reading. Nobody is required to take a track until it has approved questions. **Write questions** on the same page (admin only, `lib/profileQuestions.ts`, shared generator in `lib/questionGen.ts`) writes 10 multiple-choice questions for each level a person must pass (1 to the track's `requiredLevel`) from the published text; a second blind pass answers each one and only agreeing, unambiguous ones are kept. They arrive as "review" and go live only when an admin approves them at `/admin/review/<track>`; pressing the button again tops up levels still short of 10. It needs `ANTHROPIC_API_KEY` on the server and says so if it is missing; a rejected key stops the run. `npm run generate:bank -- --track <slug>` does the same from the command line, for any track and up to level 20. `npm run check:access` tests it with a fake model.
- **Reward policy** (`lib/rewards.ts`, `/admin/rewards`, `/rewards`): what the first pass of a level earns, set by whoever owns the content. A rule is per company, brand or track, per level and reward (certificate, bonus XP, voucher or money); the track's rule beats its brand's, which beats its company's, and an "off" rule switches a reward off below it. With no certificate rule the default stays (a certificate at levels 5, 10, 15, 20). Every award is a row in `reward_awards`, unique per person, rule, track and level, so a retake never pays twice. Bonus XP counts toward the player level. Vouchers and money need a cap (most people who can earn it) and start "pending": gglearn never holds or moves money, so the company sends it and marks it sent with a reference (or void, which frees the place under the cap). ## Dynamic questions (never the same exam twice)
- `lib/dynamic/` holds ~70 question *families*: seeded generators that build a fresh multiple-choice question every time (new numbers, code, names, tables, snippets) and work out the right answer in code. Each level exam draws 7 of its 10 questions from them (`DYNAMIC_PER_RUN` in `lib/dynamic/store.ts`; the rest come from the stored bank), and a learner is never shown the same generated prompt twice on a track.
- `lib/dynamic/tags.ts` maps each track to families (the first tag is the track's own subject and is drawn about twice as often). A track with no tags uses stored questions only.
- A generated question is saved as a one-off snapshot row (`source = dynamic`, `status = generated`), so grading, the review page and certificates work unchanged. These rows never enter the stored pools, drills or placement.
- `npm run check:dynamic [familyPrefix] [samples]` re-derives answers by really running node, python, php, sqlite, git, npm semver and the TypeScript compiler, and fails on any mismatch. Families without an executable oracle (CSS maths, REST, cloud/marketing maths, framework rules) are checked for structure only; review them by hand when you change them.
- `npm run coverage [-- --min 100 --fail]` counts, for every track and level, stored questions plus distinct generatable prompts, and lists the levels still under 100.
- Subjects that are company knowledge rather than computable (the `sdlc-*`, `gglink-*`, `moksy-*`... curriculum tracks) cannot be generated. `npm run generate:bank -- --track <slug>` authors them with Claude from the track's knowledge items, has a second blind pass audit every answer key, and saves them as `review` (add `--activate` to publish). It needs `ANTHROPIC_API_KEY`.

## Known gaps
- Legacy bank is thin at levels 16–20 and has no brand-specific content. Real brand knowledge must be authored.
- `git-extreme.json`, `google-cloud-expert.json`, `google-cloud-intermediate.json` are invalid JSON and were skipped.
- SQLite for local dev. Move to Postgres before multi-user production use.
- Email/password auth only. No password reset, rate limiting or SSO yet.

## Deploy
Production: https://gglearn.gglink.co.uk — Apache (TLS via certbot) reverse-proxies to a PM2 app `gglearn-web` on 127.0.0.1:3400.
Server uses Node 20, so avoid Node 21+ APIs (e.g. `Map.groupBy`) and keep `better-sqlite3` on a version with a Linux Node 20 prebuild (12.9.0).
`deploy/deploy.sh` syncs, installs, builds, pushes the schema and reloads PM2. `deploy/*.conf` is the Apache vhost.

### One-time deploy failure on a database that has the old certificate column
Until the `companies.cert_valid_months` column was made nullable, `drizzle-kit push` failed on every deploy after the first one that added it, with `index companies_slug_unique already exists`. The first deploy that carries the fix still stops at the push (it rebuilds `companies` to the nullable column and keeps every row, then hits the same error); run the Deploy workflow again and it passes, and every push after that is clean. Do not add `--force` to the deploy's push.

### Auto-deploy (GitHub Actions)

`.github/workflows/deploy.yml` runs `deploy/deploy.sh` on every push to `main` (or manually via "Run workflow"). Required repo secrets: `DEPLOY_SSH_KEY` (private key authorised on the server), `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` (output of `ssh-keyscan <host>`), and optionally `DEPLOY_PORT`.
